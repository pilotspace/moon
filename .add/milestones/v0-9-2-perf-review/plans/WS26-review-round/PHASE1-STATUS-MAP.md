## 2. The key hunt: maintenance duties by runtime

Loop structure:
- **tokio**: separate `TimerImpl::interval`s (event_loop.rs:937–1007), each a `select!` arm. `tokio::time::interval` completes its **first tick immediately** and defaults to `MissedTickBehavior::Burst`.
- **monoio**: one 1 ms interval raced against the SPSC Notify (event_loop.rs:2173–2191). Chores are gated on `monoio_tick_counter % N == 0`. The counter is incremented **before** the checks (event_loop.rs:2361), so a chore of period N first runs at counter N, i.e. **~N ms after loop start, never at t=0**.

### #1279 explained

**Symptom:** on monoio, boot 1's dead files sit in `cold_files_pending_unlink:7` with `cold_dead_slots:1313` until the test times out. On tokio, the same test passes 3 of 3.

**Mechanism (verified by reading the code):**

1. `cold_files_pending_unlink` equals `pending_unlink.len() + hold.len()` (cold_index.rs:661–663), so held files count as pending.
2. `UnlinkHold::observe` sets `hold_below = next_file_id` on the **first** view it ever gets (unlink_hold.rs:98–102). `admit` then holds every zero-ref file with `file_id < hold_below` until `stamp < committed_floor`, which means until a **committed AOF fold** (unlink_hold.rs:123–140). The module doc (:33–35) intends the first view to mean "the generation recovered at boot".
3. The only callers of `observe_fold` are the orphan sweep (timers.rs:495 and :525). No view is taken at shard init: `ColdIndex` is created at boot (shard/mod.rs:289–291, main.rs:1435), but nothing observes it there.
4. **tokio:** `interval(1 s)` (event_loop.rs:965) fires immediately, so the first view is taken at loop start, before any client write. `hold_below` equals the boot counter. Every boot-1 spill file is at or above it, so it is unlinked as soon as it goes zero-ref, and the test passes.
5. **monoio:** the sweep first runs when `monoio_tick_counter` reaches `1*1000` (event_loop.rs:2695–2697 plus the pre-check increment at :2361), about 1 s after loop start. The test fills right after `await_loaded` (tests/cold_file_id_reuse_1067.rs), so the first files are minted **before** the first view. They fall below `hold_below` and are held.
6. Held files are released only by a committed fold. The monitor dispatches one only for Growth (min size 64 MB, not reached), Forced, or ColdReclaim (auto_rewrite.rs:366–386). `held_files_pressure` is raised only when `over = ledger_bytes > threshold` (cold_reclaim_tick.rs:150–155 → cold_reclaim.rs:265–276). The threshold is maxmemory/4 = 128 KiB. The ledger is 1313 slots × (40 B `DeadSlot` {Bytes, u64}, dead_slots.rs:55 + ~8 B key), about 63 KiB. So `over` is false, no fold is ever dispatched, and the files are held forever. The arithmetic is inferred from the reported counters.

**Production impact (inferred):** at the default `--cold-orphan-sweep-interval-secs 60`, a monoio server over-holds every spill file minted in its first ~60 s after each boot. Those files stay on disk until a growth or manual rewrite, or until the ledger crosses 25% of the shard budget. Without an AOF, the same first-view timing applies to the snapshot hold (snapshot_hold.rs:15–19; timers.rs:458), so held files wait for a manual BGSAVE. That no-AOF case is also inferred.

**The fix has two parts.** Only the second one closes the liveness gap on both runtimes.
- Take the first `FoldView` at shard init, before the loop accepts writes, on both runtimes, instead of depending on tokio's first tick being immediate.
- Give a held file a release trigger that does not need ledger pressure. For example: raise `held_files_pressure` when held files have waited more than K sweeps, or when `hold.len() > 0` with no fold for T seconds. Otherwise tokio leaks too as soon as any fold cut moves `hold_below` above live spills.
- Add a both-runtime regression test: boot, spill within the first sweep interval, delete everything, and assert `cold_files_pending_unlink` reaches 0.

**Related tokio variant:** #1279 comment and FIX-WINCI NOTES F2 report `cold_files_dead:1`, `pending_unlink:0`, `spill_completion_superseded:2`. This is a different mechanism. A spill completion superseded by a DEL leaves a manifest-Active file that the index never references, so it never enters `pending_unlink`. `cold_files_dead` is computed as manifest files minus referenced files (connection.rs:675–682). This is the #869 class (index-driven sweep, no filesystem reconcile) and does not depend on the runtime. Inferred, not traced end to end.

### Other items worth a ticket
- **B2: tokio eviction DELs are not logged** (table above). The doc comment at reason_del.rs:173–176 says "a tokio-runtime build never needs this leg". That is true for replication but false for the AOF leg.
- **Per-PR CI blindness:** hosted per-PR CI is tokio-only, the monoio main-push runner is offline (#1279 body), and the tokio leg excludes `graph` and `text-index`. Result: monoio-only bugs (#1279, #761, #1103) and all graph/text code have no per-PR signal.
- **Phase asymmetry in general:** every tokio chore runs at t=0 and no monoio chore does. Any future "first observation sets a baseline" logic will diverge the same way. A shared `Chores` scheduler driven by one clock would remove the class. Note that `IDLE_PARK_MS` alignment requires every `% N` to stay a multiple of 10 (event_loop.rs:2710–2716).
