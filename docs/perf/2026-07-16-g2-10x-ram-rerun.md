## Findings

1. **Spill batching works at G2 scale.** 840 heap files for the full 2.6 GB
   spill (vs ~236K one-per-key), and the file count no longer appears
   anywhere in the restart critical path.
2. **`used_memory` is now the logical ledger.** Exactly at cap under
   steady-state eviction pressure; the post-restart transient (AOF replay
   re-heats keys → demote + eviction drain) clears in ≤5 s. Operators
   sampling `INFO memory` in the first seconds after a restart will see the
   drain in progress — documented in `docs/guides/monitoring.md`.
3. **Restart cost has moved from spill files to AOF replay.** 16.9 s for a
   3.3 GB / 340K-command incr AOF with no rewrite. This is the classic
   AOF-sized cost, not an offload defect; an AOF rewrite (or WAL-v3
   checkpoint-anchored truncation) keeps it bounded. Worth tracking as a
   tuning note, not a G2 failure.
4. **Task #59 tail improved 9.3× but is not closed.** 205 ms worst cold GET
   during an active spill flood (was 1,910 ms). The per-shard
   read-vs-spill-writer fairness design decision is still pending.
5. **NEW: `DBSIZE` under-reports under disk-offload** — 24,275 vs ~164K
   logical keys (cold-index holds ~179K entries across shards; spilled keys
   leave the hot table). Pre-existing semantics gap (also true during live
   spill, not introduced by this batch); Redis parity says DBSIZE should
   count logical keys. Filed as a follow-up.

## Verdict

All three G2 acceptance criteria hold on the post-fix build, now with
truthful memory accounting and a batched spill format. v0.8
PRODUCTION-CONTRACT rows `MEM-10X-01` and `CRASH-02` updated with this
evidence.
